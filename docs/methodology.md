# Methodology

How every number this project publishes was produced, and what each one is not.
Kept separate from the README so the front page can stay short without the
caveats being quietly dropped.

## Counting the ecosystem

Published counts for the MCP ecosystem disagree by a factor of eight. Not
because anyone is lying, but because **a registry entry is a registered name,
not a server**, and no published methodology states which was counted.

Three choices each move the number by more than 20%.

| Rule | Entries | Why |
| --- | ---: | --- |
| Dropped: no source to read | 8,004 | Hosted services with no repository. Nothing for a static analyser to read, and we never run a server to find out. |
| Collapsed: already counted | 5,270 | Separately registered names pointing at a repository another entry already named. |
| **Scanned: distinct repositories** | **21,356** | What the index is actually about. |

Against 34,630 entries seen. The arithmetic closes by construction, so nothing
can disappear between two numbers.

One account alone holds **2,332 registered names pointing at a single
repository**, with 2,113 generated descriptions. Counting names rather than
repositories would make that one account 9% of the published index.

[`docs/coverage.md`](coverage.md) is regenerated by every crawl and carries the
current figures.

## Two populations, deliberately kept apart

The registry can be read to the end, so the same crawl gives the same number. A
code host cannot: it serves at most 1,000 results for any one query at ten
requests a minute. Merging the two would make our headline figure depend on how
long our own crawler ran.

So the registry census and the code-search sample are reported separately,
everywhere.

**The sample is the most surprising thing measured so far.** One twenty-minute
pass found 13,694 repositories carrying an MCP server toolkit, and **13,291 of
them appear in no registry at all** — 97%, consistent across two independent
queries. Over 100,000 files on GitHub carry the JavaScript server toolkit and
over 170,000 the Python one, against a registry that collapses to 21,356
repositories.

A search cannot tell a server from something that merely talks to one, so each
candidate is checked against its own source. Both SDKs put servers and clients
on different import paths, which makes the check a fact about the code rather
than a guess: **89% of a sample of 100 carried a server import**, and the rest
are scanned but withheld from the index.

Registry entries skip that check. A publisher asserted they are servers, and
the registry carries servers in Rust, C# and Go that a Python-and-TypeScript
check would reject for being written in the wrong language.

## Repositories that no longer exist

**19% of a random sample of 150** distinct repositories are deleted or private,
measured by asking the code host rather than assuming. A second sample of 60
during a full scan gave 22%.

This is not in the coverage document yet, because the crawler does not probe:
the scan discovers it for free.

## What is deliberately not scanned

A flaw in a server's own test suite or build tooling is not a flaw an assistant
can reach. Tests, examples, scripts, benchmarks, fixtures and `*.config.ts` are
excluded the way `node_modules` already was.

Over 150 servers that exclusion removed **9 of 19** shell-execution findings.
Without it, a server with a thorough test suite would score worse than one with
a genuinely unsafe tool handler.

The cost is real: a server whose actual entry point lives under `scripts/` is
missed entirely.

## Which servers get which checks

One rule reads characters and needs no parser, so it runs against every server
whatever its language. The four deeper rules parse code, and in v1 they cover
TypeScript and JavaScript.

That is where the ecosystem is. Measured across **463 repositories** from both
populations:

| | registry | unregistered |
| --- | ---: | ---: |
| TypeScript | 33% | 39% |
| Python | 26% | 38% |
| JavaScript | 16% | 11% |
| Everything else | 24% | 12% |
| **TypeScript + JavaScript** | **50%** | **50%** |

One grammar covers the whole JavaScript family, including JSX inside `.js`
files, so half the ecosystem costs roughly one language's work.

This reversed an earlier decision. The original plan put Python first, argued
from "roughly 45% Python and 30-35% TypeScript" — a figure that predated having
a corpus to measure. See `DECISIONS.md` D3 and D6.

Python servers get the character check in v1 and the deeper rules first after
it. **Results always state which servers got which**, and a figure derived from
one language is never presented as an ecosystem-wide one.

## The accuracy pilot, 2026-09-22

The first time anything in this project was scored rather than asserted.

**Method.** 43 real findings from 10 real servers, produced by a scan of a
random 150-server sample. Each labelled by hand by reading the surrounding
code, against a rule fixed before any scoring: *exploitable = an
assistant-supplied argument reaches the sink, and nothing constrains where it
can go.*

**Results.**

| | precision | recall |
| --- | ---: | ---: |
| Every finding the rules report | 0.81 | 1.00 |
| Only findings the rules call high confidence | 0.62 | 0.14 |
| A calibrated judgement above 0.5 | 0.89 | 0.94 |
| A calibrated judgement above 0.7 | 0.92 | 0.66 |

**This is a pilot, not the accuracy figure this project exists to publish.**
Three weaknesses, stated because a figure whose limits are known is worth more
than a better one that hides them:

1. **The sample is concentrated.** 22 of the 43 findings come from a single
   repository, so the effective sample is nearer ten servers than forty-three
   findings.
2. **The labels are not independent.** The same project wrote the rules and the
   labels. That is precisely the weakness `DECISIONS.md` D7 criticises in
   accuracy figures published elsewhere, and naming it here does not excuse it.
3. **The rubric is a choice.** A different and equally defensible rule — that a
   file-reading tool reading any file is doing its job — would move many labels.

The real figure comes from the golden set in D8: randomly sampled across the
whole corpus, labelled through a separate process, and published as an open
benchmark with its sampling method and a scoring script.

### What the pilot already changed

**The rules over-report by about a fifth**, and more usefully, **their own
confidence flag is not a quality signal**. Findings marked high confidence
scored 0.62 precision against 0.81 for reporting everything — the flag selects
a *worse* set than no filter at all.

It means "the taint path is unambiguous", which turns out not to predict
whether anything is exploitable. That assumption shaped two rules and survived
only because nothing had ever scored it. Reworking it is now scheduled rather
than guessed at.

## Adjudicating the ambiguous half

A rule can be certain about `execSync(userInput)` and not about
`execSync(escape(userInput))`, which is a judgement about whether that escaping
is any good. There are thousands of those a night: too ambiguous for a rule,
too small to be worth a large model call each.

The requirement, recorded as D12, is that whatever judges them returns a
**calibrated probability**, and that the threshold applied to it is published.
A number that means what it says can be tuned and reported as precision and
recall at the chosen cut-off. A verdict in prose carries no confidence anyone
can inspect.

**No model is chosen.** A System One decision model is the leading candidate
and the pilot above is the first evidence the requirement is achievable, but
committing before measuring properly is the failure D7 exists to prevent.

Measured while testing it: 660ms median per decision, and **$1.72 for a full
corpus run** at the ~6,400 low-confidence findings two rules produce.

One failure worth recording. The first integration sent the flagged expression
alone, with no surrounding code, and every finding came back clustered at 0.7 —
a human could not have judged from that either. Twelve lines either side more
than doubled the spread.

## Cost and runtime

| | measured |
| --- | --- |
| Registry crawl | ~90 seconds, 343 pages |
| Code-search pass | ~20 minutes, bounded at 200 requests |
| Full scan, 35,050 repositories | ~2.0 hours at 8 workers |
| Parsing overhead | 66 ms per repository |
| Adjudication | ~$1.72 per corpus run |

Sequential scanning would be 9.5 hours and would not fit a six-hour job limit,
which is why the orchestrator is concurrent.
